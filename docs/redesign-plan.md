## 1. Audit: what exists today

~9.9k lines of Swift in one app target, generated by XcodeGen (`project.yml`). Swift 6, strict concurrency complete, iOS 17 deployment target, Xcode 26.5 installed. **No test target and no tests exist.** "Keep existing tests passing" is therefore vacuous today; M0 adds the first test target.

### 1.1 Auth and token lifecycle (keep untouched)

| Piece | File | What it does |
|---|---|---|
| Spotify sign-in | `Core/Networking/SpotifyAPI/SpotifyAuthManager.swift` | `@MainActor @Observable`. PKCE via `ASWebAuthenticationSession`, BYOK client ID stored in Keychain, profile fetch (`display_name`, `product`, images), `logout()`, `refreshAuthStatus()`. Writes tokens; does not refresh them. |
| Token provider | `Core/Networking/SpotifyAPI/SpotifyTokenProvider.swift` | Actor. `validAccessToken()`, `forceRefreshedToken(rejecting:)`. Process-wide `SpotifyRefreshGate` serializes refresh to avoid the rotation `invalid_grant` race; only a 400 clears credentials. |
| Keychain | `Core/Storage/KeychainManager.swift` | Static wrapper; keys under `com.kounex.antiphon.spotify.*`. No access group. |
| Apple Music | `Core/Networking/AppleMusic/AppleMusicManager.swift` | `@MainActor @Observable`, `nonisolated init`. `MusicAuthorization.request()`; `ensureAuthorized()` checks live status so fresh background instances work. |

Gaps the redesign needs, all additive at call sites only: a "signed in since" timestamp written after a successful login; an Apple Music subscription and storefront query (`MusicSubscription.current`, `MusicDataRequest.currentCountryCode`); and a saved-tracks total for the onboarding summary (`/me/tracks?limit=1`, using the existing `user-library-read` scope). The `product` field only comes back with `user-read-private`, which we don't request. I won't add scopes, because that forces everyone to sign in again, so "Premium" is shown only when the API returns it.

### 1.2 API clients (reuse)

- `SpotifyAPIClient` (actor): playlists (all and editable), playlist items (`/items`, adapted to the Feb 2026 API), create, add (100/batch), **remove (exists, unused)**, ISRC search, query search, image upload; 429 `Retry-After` and 401-refresh retry.
- `AppleMusicManager`: library playlists (paged), playlist tracks with batched catalog-ISRC resolution and local lookup, create playlist, add tracks one at a time with `partialAdd` error, artwork-as-JPEG, ISRC and catalog search. **No remove and no reorder.**
- Models already carry `explicit`, `collaborative`, `owner`, `snapshotId`, `addedBy`, `product`.

### 1.3 Matching (reuse; extend so it returns a score instead of a yes/no)

`TrackMatcher` (struct): finds by ISRC, then fuzzy search (top 5 results) with `matchScore` = title 0.45 + artist 0.40 + duration 0.15 (±5 s), and accepts ≥ 0.6. `isMatch` overloads check whether a track is already in a playlist (≥ 0.75). Normalization lives in `String+Extensions` (keeps remix tags, strips promotional junk). **The best candidate is returned without its score, reason or alternatives**, so confidence bands need an additive API.

### 1.4 Sync engine (reuse; add a separate planning step)

- `SyncEngine` (actor, 981 lines). Stage A: `CacheAligner` aligns the source into `CachedTrack`; `PlaylistCachePruner` dedupes and prunes; `DeltaEngine` runs ISRC then fuzzy target matching, detects destination-only tracks, flags removals, and re-anchors Apple Music library IDs. Then a removal **safety threshold of 50%** (the README says 30%; the code is the authority). Stage B: per-track search, then batched writes, with careful rollback of unwritten tracks to `.pending`, resume after interruption, and a cross-engine lock (`inProgressSyncPairs`).
- **Matching and writing happen in one pass.** Stage A mutates and saves the cache (`try? context.save()` inside the aligner and delta), and Stage B writes as soon as it has matches. **There is no dry run.**
- Removals are only flagged (`RemovalFlag`), never executed. "Keep" sets `removalKeptAt`; "Dismiss" clears `unmatchedPlatform`.
- `SyncCoordinator` (`@MainActor @Observable`) holds per-pair tasks, progress, cancellation and wait-for-unwind.

### 1.5 Persistence (extend with a versioned migration)

SwiftData `SyncPair` 1→n `CachedTrack`, 1→n `SyncLog` (cascade), in a single shared container (`SharedModelContainer`) in the app sandbox. **No `VersionedSchema` yet.** `SyncDirection` raw values are user-facing strings stored on disk ("Spotify → Apple Music"), so they must stay byte-identical.

### 1.6 Background, intents, notifications

- `BackgroundTaskManager`: one `BGAppRefreshTask` (`com.antiphon.playlistRefresh`), global interval from `@AppStorage("syncIntervalMinutes")` (default 30), reschedules on background and on run, posts a failure notification, honors expiration.
- `SyncPlaylistsIntent` plus `AntiphonShortcuts` (Siri and Shortcuts "Sync playlists").
- `NotificationManager`: permission requested on first `.active`, grouped failure notifications. No categories or actions.
- Entitlements: empty. **No App Group**, no widget or extension targets, no ActivityKit.

### 1.7 UI (to be replaced)

`DashboardView`, `PlaylistInspectorView` + `InspectorTabViews` (tracks, flagged, history with collapsing), `ManualMatchSheet`, the `LinkWizard` (4 steps), `SettingsView` + `ConnectionCards` + `BYOKGuideView`, and the `UI/Theme` (old palette and gradients). The **logic** inside these views moves into view models and services: diagnostics export, history grouping, manual-match search, the BYOK guide and Reset All Data. The views themselves are deleted once their replacements ship.

## 2. Platform constraints that shape the design

1. **Background timing.** `BGAppRefreshTask` runs when iOS decides. "Every 15 min" is a request, not a promise. Copy says "About every 15 min. iOS decides the exact moment." The storyboard's "Checks every 15 min, even when Antiphon is closed" gets reworded. The design-system README's "server watcher" doesn't exist and is dropped.
2. **Live Activities can't be started from a background refresh** (only from the foreground, push-to-start, or a `LiveActivityIntent`). Syncs over 20 s that start in the foreground or from the widget get one; background runs don't.
3. **Interactive widget buttons run in the widget process**, unless the intent is a `LiveActivityIntent`, which runs in the app. That's the basis for D4.
4. **Spotify app restrictions for new BYOK apps** (Nov 2024 and Feb 2026): no `preview_url`; algorithmic and Spotify-owned editorial playlists return 404. Those rows show as disabled, with the reason.
5. **Apple Music remove and reorder:** unknown on iOS. Spike in M0 (D1).
6. **Spotify → Apple Music cover:** `createPlaylist` in MusicKit takes no artwork. "With the same description and cover" becomes "with the same name and description." The existing Apple Music → Spotify artwork upload stays.
7. **Spotify `added_by`** gives a user ID, not a name. "Added by Joana" would cost one request per collaborator; we show "added by you" or "added by a collaborator."

## 3. How the design's behavior rules map to the engine

- **Dry-run first.** Every sync a person starts (first sync, Sync now, a review decision that writes, conflict resolution, undo) shows a preview sheet whose numbers come from a `SyncPlan`. **Background monitoring** builds the same plan and applies only what the seam's rules allow without asking: auto-band adds always, plus opted-in mirror removals (per D2). Everything else waits in the review or conflict queues, with an actionable notification. The design's "Close matches don't sync until you approve them" applies to both paths.
- **Nothing removed by default.** New seams default to `removalPolicy = .keep` (one way) or `.ask` (both ways).
- **Two-way removal → conflict question** with three outcomes: remove on the other side, restore on the side it was removed from, or keep the difference (the track is ignored in this seam; this reuses `removalKeptAt`). The detection time is when Antiphon *noticed* the removal, so the copy says "Noticed yesterday at 22:14", not "Removed".
- **Confidence bands.** `confidence >= threshold` (default 90) → add automatically. `60 ..< threshold` → review queue. `< 60` → not added, shown as alternatives. Only the upper bound moves with the setting; 60 stays the floor, as in the ConfidenceMeter spec. Reasons, strongest first: ISRC match (100); title + artist + duration within 2 s; title + artist with a version difference (remaster, live, explicit/clean, radio edit); title only.
- **Every run is logged and can be undone.** Every write that lands creates a `SyncChange`. Undo builds the inverse ops, previews them in one sentence ("Removes these 4 tracks from Apple Music and puts the moved one back."), runs them as a new run marked `undoOf`, and skips (and reports) any op that no longer applies.

## 4. Proposed model changes (SwiftData, lightweight migration)

Introduce `AntiphonSchemaV1` (today's models, unchanged) and `AntiphonSchemaV2`, plus a `SchemaMigrationPlan` with one lightweight stage. Every new stored property is optional or has a default. New enums are `String`-backed. Existing raw values don't change. M0 includes a migration test that opens a V1 store fixture with V2.

### 4.1 Seam → `SyncPair` (extend)

```swift
// existing: syncDirection: SyncDirection (.bidirectional / .spotifyToApple / .appleToSpotify), isMonitored
var removalPolicy: RemovalPolicy?        // .keep | .mirror | .ask   (nil → .keep one-way, .ask two-way)
var monitorIntervalMinutes: Int?         // nil → global default; 0 → "Only when I ask"
var orderSource: Platform?               // nil → source side (one-way) / leading side (two-way)
var newTrackPlacement: TrackPlacement?   // .end only for now (.matchSource once reorder is proven)
var notifyNewTracks: Bool = false
var pausedAt: Date?                      // "Pause this seam" (distinct from monitoring off)
var spotifyCreatedByAntiphon: Bool = false
var appleMusicCreatedByAntiphon: Bool = false
var lastViewedAt: Date?                  // drives the "New" chip on seam detail
```

Computed, no storage: `isTwoWay`, `sourcePlatform`, `effectiveRemovalPolicy`, and `swapped()` for "Swap direction". Swapping, or switching between one way and both ways, invalidates the cache's source semantics, so it triggers a full-rebuild **plan** shown as a preview before anything is written.

### 4.2 Track match → `CachedTrack` (extend)

```swift
var matchConfidence: Int?                // 0–100
var matchReason: MatchReason?            // .isrc | .titleArtistDuration | .versionDifference | .titleOnly | .manual
var counterpartISRC: String?             // ISRC of the matched track on the other side (existing `isrc` is the source's)
var candidatesData: Data?                // JSON [MatchCandidate] (top 5, value type), for alternatives & review
var unavailableReason: UnavailableReason? // .notInCatalog | .regionLocked(storefront)
var nextAvailabilityCheckAt: Date?
var addedByUserId: String?               // Spotify collaborative playlists
// TrackSyncState gains .needsReview
```

`MatchCandidate` is a `Codable` value type: platform, catalog ID, title, artist, album, year, duration, ISRC, explicit, artwork URL, confidence, reason. I'm storing candidates as JSON `Data` instead of a relationship to avoid SwiftData's composite-array pitfalls, and because candidates are never queried.

### 4.3 Sync run log with undo → `SyncLog` (extend) + new `SyncChange`

```swift
// SyncLog additions
var trigger: SyncTrigger?                // .firstSync | .manual | .monitor | .shortcut | .widget | .review | .conflict | .undo
var startedAt: Date?; var duration: TimeInterval?
var tracksMoved: Int = 0
var undoneAt: Date?
var undoOfRunId: UUID?
@Relationship(deleteRule: .cascade, inverse: \SyncChange.run) var changes: [SyncChange] = []

@Model final class SyncChange {
    var id: UUID
    var run: SyncLog?
    var platform: Platform               // where the write landed
    var kind: ChangeKind                 // .add | .remove | .move
    var platformTrackId: String          // Spotify URI or Apple Music catalog/library ID
    var isrc: String?
    var title: String; var artist: String; var artworkURL: String?
    var fromIndex: Int?; var toIndex: Int?
    var confidence: Int?; var reason: MatchReason?
    var seenAt: Date?                    // Activity › New tracks, "Mark all seen"
}
```

### 4.4 Conflicts and problems

- **Conflicts aren't a new model.** They're a value-type projection (`SeamConflict`) over `CachedTrack` rows in two-way seams with `.removedFromSpotify` / `.removedFromAppleMusic`, so there's one source of truth. Resolution writes to the row and, if needed, runs a logged sync run.
- **Problems are a new model**, because background runs produce them and notifications refer to them:

```swift
@Model final class SyncProblem {
    var id: UUID
    var kind: ProblemKind                // .signedOut(platform) | .playlistDeleted(platform) | .rateLimited(platform) | .writeRefused | .subscriptionLapsed
    var pair: SyncPair?                  // nil = affects all seams (e.g. sign-out)
    var message: String
    var firstSeenAt: Date; var retryAt: Date?; var resolvedAt: Date?
}
```

"Signed out" is derived live from auth state (`SpotifyAuthManager.isAuthenticated`, `MusicAuthorization.currentStatus`) and also recorded, so the background notification and the problems list agree.

### 4.5 Preferences (UserDefaults, not SwiftData)

`AppPreferences`: auto-add threshold; new-seam defaults (removal policy, monitoring, interval); version preferences (explicit/clean/same as source, original over remaster, never live unless the source is, allow radio edits); unavailable recheck cadence; monitoring gates (Wi-Fi only, pause in Low Power Mode, quiet hours); notification categories (decide, breaks, new-tracks summary, weekly digest); `hasCompletedOnboarding`. The existing `syncIntervalMinutes` key is read as the migration source.

## 5. Architecture

```
Packages/AntiphonDesign   (local SPM package, imported by app + widget + share ext)
  Tokens: Color assets (dark/light) from tokens.json, AntiphonFont (Dynamic Type styles + metric/code), Space, Radius, Opacity
  Components: SeamLine, StatusPill, SyncCard, TrackRow, ConfidenceMeter, DirectionPicker,
              MonitorToggle, PlatformBadge (+ marked official-badge placeholders), GlassButton styles,
              SyncAccessory, TabBar scaffold
  Accessibility helpers: reduce-motion stitch, increase-contrast hairline, AX5 layout switches
Antiphon (app)
  Core/…            existing services, unchanged except the additive seams below
  Services/         protocols + live adapters + PreviewServices (mock fixtures)
  Sync/Planning/    SyncPlanner, SyncPlan, ConfidenceScorer, VersionTag, UndoPlanner, ConflictResolver
  Features/<Tab>/   View + @Observable ViewModel per screen
  Debug/            ComponentCatalogView, launch-argument screen router (DEBUG only)
AntiphonWidgets      widgets + Live Activity (ActivityKit), shares SyncAllIntent + ActivityAttributes sources
AntiphonShare        share extension (App Group queue, per D3)
AntiphonTests        Swift Testing
```

**Service protocols** (all `Sendable`; views only see value types):
`AccountsService`, `LibraryService` (playlists on both sides, tracks, overlap, availability), `SeamRepository` (summaries, rules, observation through `ModelContext.didSave`), `SyncService` (`plan`, `apply`, `undoPreview`, `undo`, `decide(review:)`, `resolve(conflict:)`, progress `AsyncStream`), `ActivityService`, `ProblemsService`, `PreferencesStore`. Each has a live adapter over the existing managers and a mock in `PreviewServices` filled with synthetic fixtures.

**Splitting planning from writing (the one real engine change):**

1. **Value-type catalog layer.** MusicKit's `Song` can't be constructed in tests, so matching and planning run on a `CatalogTrack` value type. `Song` and `SpotifyTrack` are mapped at the edges, and `Song` is re-fetched by ID when writing. `TrackMatcher` gets `bestMatches(…) -> MatchOutcome {best, confidence, reason, alternatives}`. The existing `find…` methods become thin wrappers with identical behavior.
2. **`SyncPlanner`.** Runs the existing Stage A on a scratch `ModelContext` (autosave off). The aligner, pruner and delta get a `persist: Bool = true` parameter so their internal `save()` calls can be skipped, and the scratch context is rolled back afterwards. It then resolves pending tracks through the matcher and returns a `SyncPlan`: adds by side and band, removals, conflicts, unavailable tracks, the resolved IDs, and the Spotify snapshot ID and Apple Music track count it saw.
3. **`SyncEngine.apply(plan:approvals:)`.** Reuses the existing path. It checks whether the plan is stale (Spotify snapshot ID or Apple Music count changed) and re-plans if so. Stage B uses the plan's resolved IDs instead of searching again, holds back tracks below the threshold as `.needsReview`, and keeps the **existing batch-write and rollback code untouched**. It records a `SyncChange` for each write that lands, and carries out approved removals through `removeTracksFromPlaylist` on Spotify, plus the Apple Music path depending on D1.
4. **Monitoring.** One `BGAppRefreshTask` picks the seams that are due (per-seam interval, `lastSyncedAt`, paused, gates), runs plan → auto-apply, and reschedules for the earliest next due time.

## 10. Risks

| Risk | Mitigation |
